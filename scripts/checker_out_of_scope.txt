# Conformance files the checker will NOT be taught to flag.
#
# `checker_conformance_oracle.sh` reads this and reports the MISS bucket as
# two numbers instead of one: `MISS (in scope)`, which is the real backlog
# and can legitimately reach zero, and `OUT OF SCOPE`, which is declared.
# `docs/checker-triage.md` explains why one number could rank nothing —
# it summed work worth doing now with files nobody should ever fix, so it
# answered neither "are we done?" nor "what next?".
#
# Format: <path> <kind>: <reason>.  Blank lines and `#` lines are ignored;
# only the first whitespace-separated field is read as a path.
#
# THIS IS NOT A SUPPRESSION LIST. Out of scope means "we will not add a
# rule to flag this file", never "we may flag it wrongly". A false positive
# on a listed file is still a soundness bug and still counts against the FP
# budget, which this file does not touch. The oracle also reports any entry
# that has stopped being a MISS, so a path cannot sit here after the reason
# for it is gone.
#
# Every entry below was decided by OPENING the file. The triage's first
# pass keyed on the directory name and the count came out twice too large:
# `parser/ecmascript5/` holds ordinary current TypeScript as well as the
# error-recovery corpus (`parserExportAssignment6` is `declare module "M"
# { export = A }`, an undefined-name check; `parserES5SymbolProperty4` is
# `[Symbol.isRegExp]`, a lib member lookup), and a file NAMED for `using`
# can carry an error `using` has nothing to do with
# (`usingDeclarationsWithObjectLiterals2` is TS7018 on `value: null`,
# which a plain `const` reproduces under the same two flags — measured).
# Twelve legacy files became six; six `using` files became five. That is
# the label-standing-in-for-the-objective substitution CLAUDE.md records
# five times, and the only defence is the file itself.

# rule for it could never fire on an input anyone can still write.

typescript/tests/cases/conformance/parser/ecmascript5/parserRealSource3.ts removed-feature: the error is TS6053 "File 'typescript.ts' not found" from a `///<reference path=...>`, which is triple-slash path RESOLUTION — program construction rather than type checking, and the checker has no notion of a program.
typescript/tests/cases/conformance/parser/ecmascript5/parserRealSource1.ts removed-feature: same as parserRealSource3 — TS6053 on `///<reference path='typescript.ts'>` and nothing else (probed). It was a TP by ACCIDENT until batch DO: the only thing we flagged in it was `result += "\\t"`, ordinary string building, through the `+=` exemption bug fixed in that batch. `--max-miss` is what surfaced it.
typescript/tests/cases/conformance/parser/ecmascript5/parserRealSource2.ts removed-feature: same as parserRealSource1, same accidental-TP history.

# ---------------------------------------------------------------------
# lexer-adversarial — the file exists to test regex-versus-comment
# disambiguation on input written to be ambiguous.
# ---------------------------------------------------------------------
typescript/tests/cases/conformance/parser/ecmascript5/RegularExpressions/parseRegularExpressionMixedWithComments.ts lexer-adversarial: `/**// asdf /` and `/**///**/ asdf /`. Ordinary regex-after-comment lexing is correct here (both `var r = /**/ / asdf /` and `var r = /**// asdf /` scan and check clean — measured), so the gap is only that tsc resolves these particular no-space forms to DIVISION where we resolve them to a regex, which is why its diagnostics are ordinary TS2362/TS2363 arithmetic-operand errors. Flipping the file means reproducing tsc's resolution on input written to defeat it.
