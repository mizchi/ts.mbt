# `tsc-extra` — TypeScript checker behaviour the upstream suite does not test

A dataset for projects that reproduce TypeScript's type checker: a
reimplementation, a subset checker, a linter with type-aware rules. Each
case pins how TypeScript 7 behaves at a place where
`microsoft/TypeScript`'s own test suite has no test: which spellings it
accepts and which it reports, side by side. The cases came out of probing
the real compiler while building this repo's checker, mostly at false
positives it produced on real code (zod, effect, univer, excalidraw).

The cases are not meant to be submitted upstream. They are kept in the
upstream harness format only because that is the format an existing
conformance runner already reads.

The five cases under `feedback/` are a different kind. Each one pins a
TypeScript 7 behaviour that looks inconsistent, with the spelling it
compares against in the same file. A reimplementation that wants tsc's
answers has to reproduce these too. Every other case is coverage: tsc's
answer looks right and nothing upstream pins it.

## Using it from another project

Each case is one file, `cases/<area>/<name>.ts`, with a `// @option:
value` header. Run it under the header's options and compare against one
of two things:

- **The claims**, which need no diagnostic format at all. A top-level
  function, `const` or class named `ok…` (`Ok…` for a class) is a span in
  which tsc reports nothing. One named `bad…` (`Bad…`) is a span in which
  tsc reports at least one error. A checker passes a claim when it agrees.
  This is the score this repo keeps for its own checker.
- **The baseline**, `baselines/<name>.errors.txt`, for the exact codes,
  positions and messages. It is in the upstream `.errors.txt` shape, and a
  case tsc accepts has none, as upstream.

`index.json` lists every case with what a runner needs: the path, the area,
the header options, whether tsc accepts the file, the error codes it
reports, the baseline's path, and each claim's name, kind and line span.
Lines count from the first line of content, after the option header and the
blank lines below it are stripped, which is what the baseline's positions
count from too. The file is regenerated by `--update` and checked on every
other run, so it cannot drift from the cases.

The expected answers are TypeScript **7.1.0-dev.20261114.1** (the `main`
nightly at `6bdcb54d`), recorded in `index.json` as `typescript`.

## Layout

```
cases/<area>/<name>.ts      one upstream-format case (`// @option: value` header)
baselines/<name>.errors.txt TypeScript 7's diagnostics, in the upstream format;
                            absent when tsc accepts the file, as upstream
index.json                  every case, its options, codes and claims
mtsc-misses.txt             `bad…` declarations this repo's checker does not
                            report (declared); not part of the dataset
issue-drafts/<name>.md      a bug-report draft for a `feedback/` case with no
                            upstream duplicate (upstream template headings)
```

Upstream baselines are flat, so case basenames are unique across areas.
Every name is checked against the upstream test names (see below).

## Conventions

- **Header.** `// @strict: true` and `// @target: esnext` unless the case is
  about another setting. As in the upstream harness, the header lines and
  the blank lines after them are stripped before the file is compiled. Line
  numbers in a baseline count from the first line of content.
- **`ok…` / `bad…`.** A top-level function, `const` or class named `ok…`
  (`Ok…` for a class) claims that tsc reports nothing inside it. One named
  `bad…` (`Bad…`) claims that tsc reports something there. The harness
  checks every claim against tsc's own spans, so no case can call a line
  legal when tsc rejects it. Declarations with other names make no claim.
- **One cell per declaration.** A case puts each spelling in its own
  `ok…` / `bad…` function, so a checker's answer can be scored cell by
  cell, and the legal spelling sits next to the illegal one that differs
  from it in one respect.
- **Single file.** `@filename` is not supported, so a behaviour that needs
  two modules is written in one where the language allows it (two `declare
  global` blocks for one namespace, for instance).
- **Modules.** A case that augments `declare global` or shadows a lib name
  has `export {};`. In a script the same declaration means something else,
  and the case would pin the wrong thing. `moduleLocalNonNullableShadowsLibUtility`
  documents this: in a script, its alias is TS2300 against the lib.

## Verifying

```bash
just verify-tsc-extra
```

The script runs `scripts/verify_tsc_extra.mjs` against
`node_modules/typescript` (**TypeScript 7.1.0-dev.20261114.1**, the
nightly on `main` that the oracle's corpus is pinned to) and answers three
questions, in order:

1. **Baseline.** Does TypeScript 7 still produce the committed
   `.errors.txt`? A drift here is news about tsc, not about mtsc. Read the
   diff, then run `just verify-tsc-extra --update`.
2. **Claims.** Does every `ok…` / `bad…` name agree with tsc?
3. **mtsc.** `mtsc check --strict` runs the unfiltered checker. Any report
   on an `ok…` declaration fails as a false positive. So does any report in
   a file tsc accepts outright, or a parse failure on one. A `bad…`
   declaration mtsc stays silent on is a MISS. A MISS fails unless it is
   listed in `mtsc-misses.txt`, and a listed MISS that no longer misses
   fails as STALE.

The baseline generator ports the harness's `iterateErrorBaseline`: header
lines, squiggles, message chains, `!!! related` lines with `--:--` for lib
files, untruncated types, and no final newline. It was checked against the
vendored TS7 baselines. Over 500 sampled single-file upstream conformance
cases it reproduces the committed `.errors.txt` byte for byte (ignoring
CRLF) in 498. Neither of the two misses applies to a case here: one
references the harness's virtual `/.lib/react16.d.ts`, and the other is
where the harness places a removed-option error (TS5102). So a baseline
here is what upstream's own run would print, though upstream also
generates `.types` / `.symbols` / `.js` and this harness does not.

## How "not upstream" was established

- **Names.** No case basename matches an upstream test name. The check runs
  against `scripts/ts7_baselines/tsgo_ran_set.txt` every time. Pass
  `--upstream DIR` to also check every case under a checkout of
  `tsc/testdata/tests/cases` (compiler and conformance: 12,974 files at
  `v7.1-beta`, 13,053 at the `main` nightly `6bdcb54d`; checked at both).
- **Text.** With `--upstream DIR`, the harness also measures, for every
  case, the share of its significant lines (eight characters or more, not
  a comment) that appear verbatim in any single upstream case. A coverage
  case at 0.34 or above fails. Against the 5,912 conformance cases the
  maximum is **0.33**, and most coverage cases share no line with any
  upstream case (`--upstream` prints the count). A `feedback/` case is
  written against the test it questions, so its overlap is reported and
  not failed.
- **Meaning.** Text cannot show whether a case is covered in substance, so
  the nearest upstream test is named below wherever one exists. The case
  adds the cells that test lacks.

## Behaviours that look inconsistent (`feedback/`)

Each was verified on TypeScript 7.1.0-beta and again on the nightly
`7.1.0-dev.20261114.1` (`main` at `6bdcb54d`), where all five reproduce
unchanged — so none was fixed between the beta and current `main`.

The baseline is tsc's answer, inconsistent or not, so a checker matching
these baselines matches tsc. The upstream trackers (microsoft/TypeScript,
and the archived microsoft/typescript-go) were searched on 2026-11-15; the
last column says what upstream has said about each, which is the best
guide to whether the behaviour will change.

## Adding a case

Write the cell that differs in one respect from its legal neighbour, name
each one `ok…` or `bad…`, and run `just verify-tsc-extra --update`, which
writes the baseline and the index. A claim tsc contradicts fails the run,
so a case cannot call a line legal that tsc rejects. Run once more with
`--upstream DIR` against an upstream checkout to check the name and the
overlap. A case reduced from a real package goes under `realWorld/`, with
the package named in its leading comment.

## What building this found

Two defects in `scripts/lib/tsc-probe.mjs`, the probe every recorded "tsc
accepts / reports" in this repo goes through. Both gave wrong answers
without any warning.

- **Header options were dropped.** The probe passed only a fixed list of
  options to the compiler. `noImplicitOverride` was not on it, so a file
  asking for it was checked with the flag off. The checker's "a mixin base
  is exempt from TS4114" came from such a probe. TS7 reports TS4114 through
  a mixin, so the exemption is removed and the unit test that pinned it
  now expects the report. Every header option the upstream corpus uses
  that can change a diagnostic is honoured now. Any other option prints a
  warning instead of disappearing.
- **Global diagnostics were missing.** TS2318 ("Cannot find global type")
  under `@lib` / `@noLib` comes from `getGlobalDiagnostics()`. The probe
  never called it, so it reported such a file as accepted.
